# 🛡️ RWP Plugin Check

**Test a plugin ZIP before you install it.**

Plugin Check reads a plugin ZIP **in your browser** and tells you, in plain language, what is wrong with it before it
touches your site. Nothing is uploaded and nothing is installed. It is built for plugins produced by the
[AI Factory](../rwp-ai-factory/README.md) from WordPress code, but it works on any React-WP plugin ZIP.

## For site owners

1. Open **Plugin Check** in the admin menu (needs `manage_options`).
2. Drop the plugin's `.zip` on the page, or choose it.
3. Read the verdict:

   | Verdict | Meaning |
   |---|---|
   | **No problems found** | None of the common mistakes was found. It is reasonable to install. |
   | **Installable, but read the warnings** | Nothing will stop the build, but something deserves a look. |
   | **Do not install yet** | At least one problem will break the plugin or put the site at risk. |

4. If something must be fixed, press **Copy the report for the AI**, paste it into the AI Factory, ask for a corrected
   ZIP, and check the new file. Repeat until the verdict is clean, then install it under **Plugins → Upload Plugin**.

Each problem shows the file and line, what is wrong and what to do about it. **Must fix** items stop the plugin from
building or are a security risk; **Check** items are worth a look; **Notes** are for information.

## What it checks

| Area | Examples |
|---|---|
| **Structure** | `manifest.json` valid, `index.tsx` present, id not taken by a plugin that ships with React-WP, no executables, `.env` files or PHP left in the ZIP, SQL files declared in the manifest, tables listed |
| **Names** | `rwp_` functions and hooks that do not exist (the usual AI mistake, with a "did you mean"), WordPress names left unprefixed, WordPress functions with no counterpart (with the reason), `WP_Query`, `$wpdb`, PHP code, an async function used without `await` |
| **Security** | `eval`, `new Function`, `document.write`, remote code (`import('https://…')`), raw HTML injection, API keys / private keys / service keys in source, `VITE_` secrets (compiled into public JavaScript), child processes and environment variables in `server.mjs`, a server file with no authorisation check |
| **Database** | row level security missing, statements that fail on a second run (`create table` without `if not exists`, a policy without `drop policy if exists`…), core tables redefined, SECURITY DEFINER functions without `search_path`, unqualified pgcrypto calls (the cause of "function does not exist" 404s), statements the automatic database update refuses (drops, deletes, row rewrites, upserts) |
| **Imports** | files that are not in the ZIP, imports outside the plugin, core files outside the plugin API, Node modules in browser code, npm packages the build does not include |
| **Syntax** | every `.ts/.tsx/.js/.jsx/.mjs` file is parsed with the TypeScript compiler; every `.json` file is parsed |

## What it does not do

It **does not build or run** the plugin, check types, or test behaviour. It is a set of text checks tuned to the
mistakes a converter makes most; a clean report means none of those mistakes was found, not that the plugin works. The
report says this on screen ("What this check did and did not do"). Install on a copy of the site first, and only
install code you have read.

## How it works (for maintainers)

- **`lib/check.ts`** is pure (no DOM, no network): `checkPlugin(entries, { names, syntax })` returns a `Report`. It runs in
  the browser and in the node tests.
- **`lib/code.ts`** (JavaScript/TypeScript rules), **`lib/sql.ts`** (schema rules) and **`lib/check.ts`** (structure) hold
  the rules; **`lib/scan.ts`** masks comments and strings so a sample inside a prompt is never read as code, while keeping
  line numbers.
- **`lib/zip.ts`** unpacks with the same safety rules as `server/pluginInstaller.mjs` (unsafe paths, size and file
  limits, one plugin per ZIP, case clashes).
- **`lib/syntax.ts`** loads the TypeScript compiler **only when a check runs**. `vite.config.js` gives it its own
  `typescript` chunk (about 3.4 MB, 970 kB gzipped); without that group it lands in `vendor` and every visitor downloads
  it. If it cannot load, the report says syntax was not checked.
- **`data/names.json`** is generated by `npm run wp:docs` (`scripts/wpParity/pluginCheckData.mjs`) from the WordPress
  parity catalogue: the hook and function names that exist, which functions are async, and the reason each unsupported
  WordPress name has no counterpart. `tests/pluginCheck.test.mjs` fails when the committed file is stale. The catalogue
  itself (`docs/wordpress-parity`) is not shipped to client sites, which is why the plugin carries this compact copy.
- The rules in `sql.ts` mirror this repository's schema conventions and `classifyStatement` / `isNullFillUpdate` in
  `server/schemaMigrate.mjs`. Change one, change the other.

Run the tests with `npm test` (the file is `tests/pluginCheck.test.mjs`).

## Security notes

- The ZIP never leaves the browser. The report is shown on screen and copied to the clipboard only when you press the button.
- The check reads source text; it never executes plugin code.
- The screen needs `manage_options`. The checks are advisory: they do not block an upload on their own.

## Known limits

- Heuristics can be wrong in both directions. A construct hidden in a way the scanner cannot see (built from pieces, loaded
  after install) is not found; a sample that looks like code in an unusual string may be reported.
- First-party plugins that use core internals by design (`../../src/...`, `../../server/...`) show them as Notes.
- It is not wired into **Plugins → Upload Plugin**: run the check first, then upload. Doing both in one step needs a small
  change to the core upload screen.
